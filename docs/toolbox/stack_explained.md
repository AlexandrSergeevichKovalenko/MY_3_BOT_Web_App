# Toolbox — every technology in our stack, explained

This is the glossary the other docs point to. Whenever a file drops a word like "Vite", "Node",
"WSGI", "broker" — it means the thing defined here. For each: **what it is**, **why we need it**,
**where it is in our repo**, and a **link to go deeper** (official docs + a YouTube search you can
watch). Read it once end-to-end, then use it as a dictionary.

The app has four layers. We'll go layer by layer:

```
[ FRONTEND ]  what runs in the user's Telegram/browser  → JS, JSX, React, Node, npm, Vite, ESLint
[ BACKEND  ]  our server code that answers requests      → Python, Flask, WSGI, gunicorn, threads
[ DATA     ]  where data lives / is passed around        → Postgres, SQL, PgBouncer, Redis, Dramatiq
[ INFRA    ]  how it's packaged and hosted               → Docker, Railway, env vars, HTTPS/TLS, API
```

## Layer 1 — Frontend

### JavaScript (JS)
**What:** the programming language that runs inside every web browser (and the Telegram webview,
which is a browser). It's the logic: variables, functions, `if`, loops, arrays, objects.
**Why:** it's the *only* language browsers run natively, so any interactive UI is ultimately JS.
**Where:** all our `frontend/src/*.js` and the compiled output of `*.jsx`.
**Deeper:** https://developer.mozilla.org/en-US/docs/Web/JavaScript ·
YouTube: https://www.youtube.com/results?search_query=javascript+in+100+seconds

### JSX
**What:** a syntax extension that lets you write HTML-looking tags *inside* JS, used by React. It is
**not** a separate language — a build tool compiles it back into plain JS function calls
(`React.createElement(...)`). Files using it end in `.jsx`.
**Why:** describing UI as `<button>Save</button>` is far more readable than writing
`React.createElement("button", null, "Save")` by hand.
**Where:** `frontend/src/App.jsx` and every `frontend/src/components/*.jsx`.
**Deeper:** https://react.dev/learn/writing-markup-with-jsx (also fully covered in
[00a_frontend_foundations.md §1](../security_deep_dives/00a_frontend_foundations.md)).

### React
**What:** a JavaScript **library** for building user interfaces out of reusable **components**. A
component is a function that returns JSX (a piece of UI). React's core trick: when a component's
**state** changes, React re-runs that function and efficiently updates only the parts of the screen
that changed (it does this by diffing a lightweight in-memory copy of the page called the **virtual
DOM** against the real **DOM** — the browser's live tree of on-screen elements).
**Why:** without it you'd manually find and update DOM elements on every data change — error-prone
and slow to write. React lets you say "here's what the UI should look like for this data" and it
handles the updates.
**Where:** the whole `frontend/`. Version 18 (see `frontend/package.json`).
**Deeper:** https://react.dev · YouTube: https://www.youtube.com/results?search_query=react+in+100+seconds

### DOM (Document Object Model)
**What:** the browser's live, tree-shaped representation of the page — every element (`<div>`,
`<button>`) is a node you can read/change from JS. "Updating the DOM" = changing what's on screen.
**Why you'll hear it:** React exists to update the DOM *for* you.
**Deeper:** https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model/Introduction

### Node.js
**What:** a program that runs JavaScript **outside** the browser (on your Mac, on a server). It's
the JS "engine" from Chrome, packaged as a standalone runtime.
**Why we need it even though our app runs in a browser:** the *tools* that build our frontend
(Vite, ESLint, the package manager) are themselves JS programs — they need Node to run. You installed
Node to get `npm` and to run `npm run dev`. Our machine has Node v23.
**Where:** you use it via the `npm ...` commands in [running_and_testing.md](running_and_testing.md).
**Deeper:** https://nodejs.org · YouTube: https://www.youtube.com/results?search_query=what+is+nodejs

### npm (Node Package Manager)
**What:** the tool (bundled with Node) that downloads and manages third-party code **packages** your
project depends on. It reads a file called `package.json`.
**Why:** nobody writes everything from scratch — React, Vite, etc. are packages. `npm install`
fetches them.
**Where / key files:**
- `frontend/package.json` — lists your dependencies (`"react"`, `"vite"`, ...) and your run scripts
  (`"dev"`, `"build"`). This is the project's manifest.
- `frontend/node_modules/` — the actual downloaded package code. Huge, never edited by hand, never
  committed to git (it's regenerated by `npm install`).
- `package-lock.json` — records the exact versions installed, so everyone gets identical code.
**Commands:** `npm install` (fetch deps), `npm run <script>` (run a script from package.json).
**Deeper:** https://docs.npmjs.com/about-npm

### Vite
**What:** the frontend **build tool** and **dev server**. Two jobs: (1) during development it serves
your app at `localhost` and instantly reloads the browser when you save a file (called **HMR**, Hot
Module Replacement); (2) for production it **bundles** — takes all your `.jsx`/`.js` files, compiles
JSX to plain JS, merges and minifies everything into a few small files in `frontend/dist/` that
browsers can load fast.
**Why:** browsers can't run `.jsx` and can't efficiently load hundreds of separate source files.
Vite turns your source into something a browser can actually run, quickly.
**Where:** invoked by `npm run dev` and `npm run build`; config in `frontend/vite.config.*`.
**Deeper:** https://vitejs.dev · YouTube: https://www.youtube.com/results?search_query=vite+in+100+seconds
**Related terms:** *bundler* = a tool that merges many source files into few; *transpile/compile* =
translate code from one form to another (JSX → JS); *minify* = strip whitespace/rename variables to
shrink file size.

### ESLint
**What:** a **linter** — a tool that reads your code without running it and flags likely mistakes
(unused variables, misused React hooks, etc.).
**Why:** catches bugs and enforces consistency before you even run the app.
**Where:** `npm run lint`; rules in `frontend/eslint.config.*`.
**Deeper:** https://eslint.org

## Layer 2 — Backend

### Python
**What:** the programming language our server is written in. Readable, widely used for web backends
and data work. We use version 3.11.
**Where:** everything in `backend/`, plus `bot_3.py`.
**Deeper:** https://docs.python.org/3/ · YouTube: https://www.youtube.com/results?search_query=python+in+100+seconds

### pip
**What:** Python's package manager (npm's equivalent for Python). Installs packages listed in
`requirements.txt`.
**Where:** `requirements.txt`, `requirements.bot.txt`. Install with `pip install -r requirements.txt`.
**Deeper:** https://pip.pypa.io

### Flask
**What:** a lightweight Python **web framework** — the library that maps incoming HTTP requests to
Python functions. The `@app.route("/path", methods=["POST"])` decorator you saw in block 01 is
Flask.
**Why:** it handles the tedious HTTP parts (parsing requests, routing URLs, building responses) so
our code just reads `request.get_json()` and returns `jsonify(...)`.
**Where:** `backend/backend_server.py` (the routes) and `backend/web_service.py` (creates the `app`).
**Deeper:** https://flask.palletsprojects.com · YouTube: https://www.youtube.com/results?search_query=flask+python+tutorial

### WSGI
**What:** "Web Server Gateway Interface" — the standard contract between a Python web app (Flask) and
the server that runs it (gunicorn). You don't write WSGI code; it's the plug shape they agree on.
**Why you'll hear it:** it's why `gunicorn backend.web_service:app` works — `app` is a WSGI object.
**Deeper:** https://peps.python.org/pep-3333/

### gunicorn
**What:** a production-grade server that actually runs our Flask app and handles many requests at
once. Flask's own built-in server is for development only; gunicorn is what runs in production.
**Why:** it spawns **workers/threads** (parallel handlers) so hundreds of users can be served
concurrently, and it's robust under load.
**Where:** the `web:` line in `Procfile`:
`gunicorn ... --workers N --threads M backend.web_service:app`. `--workers` = how many separate
processes; `--threads` = parallel handlers per process.
**Deeper:** https://gunicorn.org
**Related terms:** *process* = one running program with its own memory; *thread* = a lighter
parallel line of execution *inside* one process (shares memory).

## Layer 3 — Data

### Postgres (PostgreSQL)
**What:** our **relational database** — permanent storage organized as **tables** (rows and
columns). Your dictionary, settings, translation checks all live here.
**Why:** it's where data survives between requests and restarts, with reliability guarantees
(transactions) and fast lookups (indexes).
**Where:** all reads/writes go through `backend/database.py` (e.g. `save_webapp_translation` writes
the `bt_3_webapp_checks` table).
**Deeper:** https://www.postgresql.org/docs/ · YouTube: https://www.youtube.com/results?search_query=postgresql+in+100+seconds

### SQL
**What:** "Structured Query Language" — the language you use to talk to a relational database:
`SELECT` (read), `INSERT` (add), `UPDATE` (change), `DELETE` (remove).
**Why the `%s` matters:** we write SQL with `%s` placeholders and pass values separately
(`cursor.execute(sql, values)`) so user text can never be interpreted as SQL — this is what stops
SQL injection (block 01 §3).
**Deeper:** https://www.postgresql.org/docs/current/tutorial-sql.html

### PgBouncer
**What:** a **connection pooler** that sits between our app and Postgres. Opening a fresh database
connection is expensive; PgBouncer keeps a small set of real connections open and lets many app
requests share them.
**Why:** without it, thousands of users would each try to open their own heavy Postgres connection
and the database would fall over. All our services connect *through* PgBouncer.
**Where:** used implicitly by `get_db_connection_context()` in `backend/database.py`.
**Deeper:** https://www.pgbouncer.org · full plain-language explanation in
[../autosave_scaling_explained.md §3.2](../autosave_scaling_explained.md#32-database-connections-pooling-pgbouncer)

### Redis
**What:** a very fast **in-memory** key-value store. Because it keeps data in RAM (not on disk), it's
used for things that must be quick and can be temporary: caches, counters, locks, and as a message
queue.
**Why:** hitting Postgres for every tiny thing is too slow/expensive; Redis absorbs the hot, fast,
short-lived data (e.g. "is this user's autosave toggle ON", rate-limit counters, the job queue).
**Where:** used across the backend for caching, idempotency locks, and as the Dramatiq broker.
**Deeper:** https://redis.io · YouTube: https://www.youtube.com/results?search_query=redis+in+100+seconds

### Dramatiq (and "broker" / "queue" / "worker")
**What:** a Python **task queue** library. Instead of doing slow work (calling OpenAI to grade 7
sentences) while the user waits, we drop a **job** onto a **queue** and a separate **worker** process
picks it up and does it in the background.
**Terms:** a *queue* is a waiting line of jobs; a *broker* is the storage holding that line (we use
Redis as the broker); a *worker* is a process that pulls jobs off the queue and runs them.
**Why:** keeps the user's request fast — the web server returns instantly with a ticket, the heavy
work happens off to the side (this is the whole async pattern in block 01).
**Where:** `translation_check_worker` in `Procfile` (`python -m backend.run_dramatiq_worker`),
actors in `backend/background_jobs.py`, the bridge in `backend/job_queue.py`.
**Deeper:** https://dramatiq.io · plain-language version in
[../autosave_scaling_explained.md §3.5](../autosave_scaling_explained.md#35-queues-brokers-workers-dramatiq)

## Layer 4 — Infrastructure

### Docker (image, container)
**What:** a tool that packages an app together with everything it needs to run (Python version,
system libraries, our code) into an **image** — a frozen, reproducible snapshot. Running an image
gives a **container** — an isolated mini-environment that behaves identically on any machine.
**Why:** "works on my laptop but not on the server" disappears — the container carries its whole
environment. Our different services are built from different Dockerfiles.
**Where:** `Dockerfile.backend`, `Dockerfile.bot`, `Dockerfile.jobs`, `Dockerfile.scheduler` in the
repo root.
**Deeper:** https://docs.docker.com/get-started/ · YouTube: https://www.youtube.com/results?search_query=docker+in+100+seconds

### Railway
**What:** our **hosting platform** (Platform-as-a-Service). It builds our Docker images from GitHub
and runs our services (web, worker, scheduler) on its machines, plus hosts our Postgres and Redis.
**Why:** we don't manage raw servers; Railway runs and scales the processes and gives us logs.
**Key behavior:** pushing to the `refactor/interface` branch auto-triggers a build+deploy (see
[backend_interaction.md §2](backend_interaction.md)).
**Deeper:** https://docs.railway.app

### Environment variables (env vars)
**What:** named settings passed to a program from outside its code (e.g. `DATABASE_URL`,
`OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`). Secrets and per-environment config live here, **not** in the
code (so they're never committed to git).
**Why:** the same code runs in dev/prod with different values, and secrets stay out of the source.
**Where:** `.env.example` lists which ones exist (with placeholder values); real values are set in
Railway's dashboard.
**Deeper:** https://12factor.net/config

### HTTPS / TLS
**What:** HTTP over an **encrypted** connection. TLS is the encryption layer. The `s` in `https://`.
**Why it matters here:** it's why an attacker on the same Wi-Fi can't read the `initData` or the
request body in transit — the whole request/response is encrypted between browser and server.
**Deeper:** https://developer.mozilla.org/en-US/docs/Web/Security/Transport_Layer_Security

### API
**What:** "Application Programming Interface" — a defined set of endpoints one program exposes for
another to call. Our `/api/webapp/...` routes are *our* API (called by our frontend). "The OpenAI
API", "the YouTube API" = other companies' endpoints *we* call.
**Why you'll hear it constantly:** every arrow between two systems in this project is "calling an
API".
**Deeper:** https://developer.mozilla.org/en-US/docs/Glossary/API

### JSON
**What:** the text format data travels in (`{"key": "value"}`). Covered fully in
[00a §4](../security_deep_dives/00a_frontend_foundations.md). Both JS and Python read/write it, which
is how our React frontend and Python backend exchange the same objects.
**Deeper:** https://www.json.org/json-en.html

### HMAC
**What:** a keyed cryptographic signature. `HMAC(key, message)` produces a fixed-length code that
only someone with the secret `key` can produce, and anyone can verify. Telegram signs `initData`
with an HMAC keyed by our bot token; we recompute it to prove the request is genuine (block 01 §3,
and fully in the upcoming block 02).
**Deeper:** https://en.wikipedia.org/wiki/HMAC
