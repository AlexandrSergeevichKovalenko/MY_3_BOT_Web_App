# Перепись угадаек на пути сохранения слова

16.08.2026. Угадайка — место, где программа решает что-то за человека по косвенному
признаку: по написанию, по длине, по регистру. Опасны те, что при этом ВЫБРАСЫВАЮТ
то, что человек сохранил, и не оставляют следа.

## Числа

```
решателей во всём коде                        71   (включая читалку, ютуб, оплату)
из них на пути сохранения слова               24
выбрасывают содержимое молча                   0   ← после починки 14.08.2026
решают молча, но ничего не теряют              1
```

⚠ В прежнем отчёте стояло «40 угадаек, 16 тихо теряют данные». Это число не
подтвердилось: считалось другой выборкой и другим правилом. Проверено функция за
функцией 16.08.2026.

## Единственная, что действительно теряла

`_detect_dictionary_entry_kind` (backend_server.py:9670). Судила по стороне, с которой
пришёл запрос. Ищешь от русского — исходная сторона русская и почти всегда многословная,
значит одиночное немецкое слово штатно объявлялось «фразой». Дальше срабатывали два
следствия: артикль не приклеивался к заголовку, и стиралась разбивка по значениям
(`payload.pop("dictionary_senses")`).

Починено 14.08.2026: судит по НЕМЕЦКОЙ стороне. Вызов `pop` убран, в коде осталось
только пояснение — чтобы никто не вернул прежнее поведение по незнанию.

## Решает молча, но ничего не теряет

`_resolve_dictionary_save_pair` (backend_server.py:9150). Если направление в запросе не
совпадает с языковой парой профиля (ни прямой, ни обратной), оно молча заменяется на
профильное. Содержимое при этом целое.

Сегодня приложение работает только с парой ru↔de, и заменять нечего. Когда языков
станет несколько (задача про многоязычность), это место пересмотреть: человек, который
сохраняет английское слово, не должен молча получать немецкую пару.

## Остальные 22 — не теряют, и вот почему

Это либо ДОСТРОЙКИ (берут первое непустое из цепочки полей — `_resolve_entry_texts_for_pair`,
`_build_dictionary_senses`), либо ЧИСТКИ С ЯВНЫМ ПРАВИЛОМ, у каждой из которых есть
заслон на случай сомнения:

| Функция | Что решает | Заслон |
|---|---|---|
| `_strip_spurious_leading_article` | убрать артикль, ошибочно приклеенный к фразе | возвращает None, если следом настоящее существительное — «der Bösewicht im Film» сохраняется |
| `_strip_german_leading_article` | отделить артикль от слова | без артикля возвращает текст как есть |
| `_normalize_german_article` | привести der/die/das к нижнему регистру | не артикль — пустая строка, дальше не используется |
| `_normalize_saved_german_single_word` | привести заголовок к словарной форме (zu-инфинитив) | правило проверяет приставку и длину остатка, иначе не трогает |
| `_apply_german_headword_normalization` | приклеить артикль к существительному | работает только при `entry_kind == "word"` и известном роде |
| `_sanitize_bilingual_dictionary_target` | не дать сохранить один и тот же текст с двух сторон | при сомнении оставляет исходное |
| `_strip_rephrase_arrow_combo`, `_strip_bilingual_ru_combo` | разлепить «оригинал → перевод», склеенные при сохранении из читалки | разлепляют только по явному разделителю |

## Как проверять это в следующий раз

Не регулярным выражением. Проверено на своей шкуре 16.08.2026: `return None` у
маленькой функции регулярка считает потерей, а комментарий с `payload.pop(...)` —
живым кодом. Оба раза число выходило неверным.

Порядок такой: обойти дерево вызовов от эндпоинта сохранения, выписать функции,
которые ПИШУТ в payload или удаляют из него, и прочитать каждую глазами. Скрипты
обхода лежали в рабочей папке сессии; сам обход занимает минут двадцать.
